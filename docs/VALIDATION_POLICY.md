# Scientific Validation Policy & Integrity Guidelines
## ISRO PS 26168: AI-ML Based Intelligent Dead Reckoning System

---

## 1. Core Principles of Validation Integrity

To meet the high standards expected by ISRO satellite-navigation evaluators, this project adheres to strict validation rules:

1. **Strict Separation of Data Modalities**:
   - **Authentic Data vs Synthetic Data**: Synthetic trajectories generated by kinematic simulators must NEVER be reported as real-world results. Any table or figure derived from simulated data must be explicitly labeled `[SYNTHETIC SIMULATION]`.
   - All primary claims and benchmark scorecard metrics submitted for PS 26168 compliance must be derived strictly from authentic IO-VNBD naturalistic driving logs (`[AUTHENTIC IO-VNBD]`).
2. **Zero Test-Set Leakage**:
   - The frozen held-out test cohort consists of 5 pre-designated driving logs: `S3b`, `Vta01b`, `Vta04`, `Vtb01`, and `Vw02` (spanning 5 distinct driver profiles and diverse speeds/routes).
   - Under no circumstances may hyper-parameters, feature selectors, scalers, or decision trees be fitted or tuned on these held-out drives.
   - All scalers and feature selectors must be fitted exclusively on the 67 training drives.
3. **Model Checkpoint Immutability**:
   - Frozen production checkpoints (e.g. `models/gbdt_speed_model_iovnbd_top45.joblib`) are permanently version-locked.
   - Retraining or altering model architecture requires an explicit, documented phase gate with complete ablation reporting.
4. **No Cherry-Picking**:
   - Outage benchmarks must report the full statistical distribution across all evaluated drives: Mean, Median, Standard Deviation, 90th Percentile (P90), 95th Percentile (P95), and Worst Case.
   - Failed or degraded drives (such as stationary starts or high-vibration periods) must be fully retained in reports with transparent root-cause analysis.
5. **Numerical Parity & Reproducibility**:
   - When porting algorithms from Python reference to C++ (`idr-core`), exact numerical parity (within double-precision floating-point tolerance $\epsilon < 10^{-6}$) must be proven on identical input vectors before certifying the port.

---

## 2. Standardized Outage Evaluation Protocol

All dead reckoning outage benchmarks must strictly follow this deterministic protocol:

| Step | Protocol Action | Parameter / Rule |
|---|---|---|
| **1** | **Deterministic Initialization** | Pre-outage window $0 \le t < t_{\text{start}}$ ($t_{\text{start}} = 20.0\text{ s}$) is strictly reserved for mounting alignment ($\mathbf{R}_p^b$) and initial gyro bias estimation. |
| **2** | **Absolute Blackout** | At $t = t_{\text{start}}$, all GNSS position, velocity, and Doppler fixes are completely withheld from the dead reckoning engine. |
| **3** | **Evaluated Durations** | Exact duration windows: $T \in \{10\text{ s}, 30\text{ s}, 60\text{ s}, 120\text{ s}\}$. |
| **4** | **Active Motion Filtering** | Drives with total ground-truth distance traveled $< 5.0\text{ m}$ within the outage window are flagged as stationary. |
| **5** | **Drift Percentage Metric** | Defined strictly as final horizontal 2D Euclidean position error divided by total ground-truth distance traveled along the road: $$\text{Drift } \% = \frac{\|\mathbf{p}_{\text{est}}(t_{\text{end}})_{2D} - \mathbf{p}_{\text{gt}}(t_{\text{end}})_{2D}\|}{\sum_{k} v_{\text{gt}}(t_k)\Delta t} \times 100\%$$ |

## 3. Evidence Classification Standards

Every reported number in documentation and claim matrices must include an explicit classification:
- **`[MEASURED]`**: Directly extracted from a logged benchmark execution script run on real data with raw output stored in `reports/`.
- **`[ANALYTICAL]`**: Derived from mathematical proofs, covariance propagation, or theoretical bounds.
- **`[SIMULATED]`**: Generated from the synthetic multi-sensor vehicle trajectory generator (`dataset_loader.py`).
- **`[TARGET]`**: Sponsor benchmark objective specified by ISRO PS 26168.
- **`[NOT VERIFIED]`**: Feature or module implemented in code but lacking empirical validation data.

---

## 4. Phase Sign-Off Requirements

A phase gate can only be declared **PASSED** when:
1. All mathematical and algorithmic requirements assigned to that phase are fully implemented.
2. All unit and regression tests pass with zero errors.
3. Full reproducibility logs, CSV metrics, and markdown reports are generated and committed to `reports/` and `docs/`.
4. No regression has occurred against previously verified modules.
